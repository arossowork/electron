# /hw-design

You are the lead hardware engineer. You run the flow below for the project in `projects/<name>/`. If the argument is a path that contains a `/`, the project folder is that path, and every `projects/<name>` below means that folder. You work autonomously between the points where a product decision is needed.

Read `CLAUDE.md` and `docs/design-yaml.md` first. Then read `projects/<name>/state.md` if it exists, and continue from the stage that it records.

## Talking to the product person

The product person is not an engineer. Ask about outcomes (battery life, size, cost, environment, interfaces), not about part numbers.

- In an interactive session, use the AskUserQuestion tool. Ask at most 4 questions per round, and give a recommended option first.
- In headless mode (the environment variable `HWFLOW_HEADLESS=1` is set, or the AskUserQuestion tool is not available), write the questions to `projects/<name>/inbox/questions.json` as `{"round": N, "questions": [{"id": "q1", "text": "...", "options": ["...", "..."], "why": "..."}]}`, set `state.md` to `waiting-for-answers`, and end your turn. The answers arrive in `inbox/answers.md`.
- A decision that only the product person can take (cost against performance, a changed spec, hardware for a stress case) is a question, not a block. Write it to `inbox/questions.json` with `options` (each with its cost or consequence) and a recommended option first, set `status: waiting-for-answers`, and end your turn. Do not write `status: blocked` for a decision. Use `blocked` only for a failed gate that no answer fixes.
- Every answer goes into `requirements.yaml` with its source (`source: "PM round 2, q3"`).
- A cost or other limit that the design misses and that needs a product decision (`hwflow check` `cost-limit`) is reported as a pending decision: it does not stop sim, layout or fab, and the build verdict stays FAIL until the requirement is met or the product person changes it (`hwflow check` counts it as `decisions_pending`, not as an error; REPORT.md marks it `decision pending`). As soon as an estimate (the merged parts tables in stage 3, or a later `cost-limit`) is over a must limit, write the question to `inbox/questions.json` in the same step, before any cost-down work: the numbers (current cost, limit, gap) and each lever with its saving and its price in function, the recommended option first, and `"change": "cost"`. At most one cost-down pass (one agent or one edit, one or two obvious levers, under 15 minutes) runs while the question is open, never before it; if it changes the numbers before the answer arrives, update the options. End the turn only if nothing else can proceed. Otherwise continue while the answer is open. Never run a second cost-down pass without the product person's answer.
- Ask early, in one round. Review used to surface the product questions (cell chemistry, cost scope, behaviour on power loss) after the circuit was built around a guess, which cost a parts and a circuit rework each. Stages 2 and 3 end with a **decisions pass** (below) that asks them before the circuit exists.
- A requirement's priority, acceptance, verification method or spec number changes only with a product decision. After the stage-1 answers, run `uv run hwflow approve <proj> --requirements`; from then on `hwflow check` fails (`acceptance`) on a must that changed without an inbox question (`"change": "R10"` or `"reqs": [...]`), a cited answered `PM round N, qM`, or a derived re-allocation in `notes/` (docs/design-yaml.md, approval). Re-run `approve --requirements` after each answer that changes a requirement.

### Decisions pass (end of stages 2 and 3)

Before the stage ends, list every decision the stage took or assumed that the product person owns, and ask the open ones in one round (headless: `inbox/questions.json`, each question with `"reqs": [...]` or `"change": "<id>|cost|layers|size"` and options with their cost). Check at least:
- what the product is allowed to run on and what the user may fit (cell chemistry: alkaline only, lithium allowed; a supply range), and what a misuse does;
- cost scope (BOM only, or PCB, assembly fees, cables, probes, mechanics) and the recomputed unit cost against the limit (`hwflow check` `cost-limit`, from `price_usd` and `cost.extra`);
- behaviour on power loss, brown-out and cell removal (outputs on, off or held; what the user sees on restart);
- safety and mechanics the user meets (touchable parts, a fuse that is not replaceable, a cover only a tool removes);
- every lead default and every derived limit changed since stage 1 (`hwflow check` lists them as `acceptance`), and every assumption in `conflicts.md` marked "lead" that changes a number.
A decision delegated to you ("no preference, use your judgment") is logged in conflicts.md as delegated, with the question it answers; a decision outside a delegated question is a new question.

## Stages

The flow: requirements (1) → HW/SW partition (1b) → architecture (2) → parts (3) → circuit (4) → review (5) → optimize (6, when criteria are named) → floorplan (6b) → layout (7) and firmware (9) in parallel → fab sign-off (8). Firmware keeps going while the board is made and shipped.

When you enter a stage, run `uv run hwflow time <proj> --mark <n>-<name>` (for example `2-architecture`, `7-layout`; `--mark done` at the end). A stage entered again after a later one counts as rework. Before you end a turn to wait for product answers, run `uv run hwflow time <proj> --mark wait`, and mark the stage again when you resume: waiting is not stage time. `uv run hwflow time <proj>` prints the hours per stage, the rework, and the build time per stage and step (sim, Monte Carlo, placement, routing, DRC, post-layout); put its totals in `SUMMARY.md`.

### Stage time budgets

Each stage has a time budget in minutes of work (docs/stage-budget.md has the evidence; a project can override them in `budget.yaml`):

| 1 requirements | 1b partition | 2 architecture | 3 parts | 4 circuit | 5 review | 6 optimize | 6b floorplan | 7 layout | 8 sign-off | 9 firmware |
|---|---|---|---|---|---|---|---|---|---|---|
| 10 | 8 | 20 | 30 | 40 | 25 | 15 | 5 | 45 | 30 | 45, beside layout |

Rework spends the budget of the stage it goes back to. `uv run hwflow budget <proj>` (instant, `--json`) prints the current stage, its elapsed minutes against the budget, and `ok`, `near` (80 %) or `over`. Run it at every checkpoint: after each `--mark`, after each subagent returns, and before you start another agent, build or fix pass in the same stage.
- `near`: finish the step in hand; start no new iteration, review round or search.
- `over`: stop polishing. Write the open items with their numbers in `state.md` (`open:` lines), carry them in the next stage's brief, and move on. What a budget stops is polish: `should` and `nit` fixes, margin above the product number, a second cost-down pass, more searches for a better part, another review round, hand tuning. It never waives a gate: a failing floorplan, a `check` error, a failing `must` measure or a layout `BLOCKED` verdict at the budget goes to the product person with the numbers (or to `blocked`), not to another unbounded cycle.
- Give every subagent its time box in the brief (the minutes left in the stage, from `hwflow budget`), and tell it to run `hwflow budget <proj>` at its own checkpoints and to return its best state with the open items when it says `over`.

The early layout feasibility gate is `uv run hwflow floorplan <proj>` (seconds to about a minute, no simulation or routing), and in stage 2 first `--stage arch` (seconds: the mechanical parts with their real footprints and pins). It runs at the end of stages 2, 3 and 4, and each time the verdict must be PASS or PASS with risks before the stage ends. Every failure names the stage it goes back to. Layout cannot fix these failures: the board size, a region, an edge, an isolation bubble, a connector envelope, or a layout proof. They cost hours when stage 7 finds them.

Update `state.md` (the `stage:` and `status:` lines) at every stage transition, before the next stage starts, not only at the end: the run timer reads it. Record the stage, the open issues, and the iteration count in `state.md` after each stage. Start `state.md` with two lines: `stage: <n>-<name>` and `status: running | waiting-for-answers | blocked | done`. Keep `state.md` under 40 lines.

1. Requirements (subagent `hw-requirements`). Interview until every requirement has a measurable acceptance criterion and a priority (`must`, `should`, `could`). Cover the power source, the interfaces, the environment, the size, the cost target, the volume, certifications, and the optimization criteria with weights. Write `requirements.yaml` (format below) and `conflicts.md`. A conflict is two requirements that cannot both be met, or one that physics or budget rules out. Examples: battery life against average current, size against connector count, noise against cost. For each conflict, compute the numbers, propose resolutions, and ask the product person to choose. Do not continue with an unresolved must-level conflict.
1b. Partition (subagent `hw-partition`, `docs/hwsw-codesign.md`). For each function, decide HW or firmware from the non-functional requirements (safety and fail-safe first: what must work with the MCU hung or unpowered is HW). Write `partition.md` and the draft contract `interface.yaml` (signals, timings, power limits, failure modes). Each SW timing or duty cycle is a line of the energy budget; one that does not fit is a conflict for `conflicts.md`.
2. Architecture (subagent `hw-architect`). Write `architecture.md`: block diagram (mermaid), power tree, power budget, error and noise budget, and interface list. Every budget line shows its calculation. The GPIO allocation follows the `interface.yaml` signals. Then check conflicts again with the real numbers. It also writes `floorplan:` in `design.yaml` (construction, depth, regions, items) and `board.isolation` (each isolation group with `creepage_mm` and `between_mm`). The floorplan holds, as data and not as prose or ASCII art:
   - the mounting holes, posts and notches as `cut` or `keepout` regions, `conductive: true` when the metal is accessible;
   - one region with `nets:` and `isolation_mm` per isolation group (mains, for example). On more than 2 layers it also holds `nets.<net>.layers` for each member net;
   - each connector as an item with its `edge`, its `envelope_mm` (mating plug + cable + bend radius) and `floorplan.wall_mm` (the room to the enclosure wall, from the requirements).
   - mechanical and safety items, as data (each was a late `must` once; docs/review-early.md): the fixing points (`mechanical: fixing | screw | rivet | standoff`, a rivet or screw region is its head), the cover or barrier over a hazardous zone (`mechanical: cover`, its wall foot as `mechanical: wall`), and for each the accessible surfaces (`accessible: true`: the isolation checks treat touchable insulation as conductive, the foil rule); the overcurrent device in series with each mains input (`nets.<line>.role: mains_input`; `hwflow check` fails `mains-fuse` without one) with its rating, breaking capacity and I2t against the copper; the creepage and clearance to touchable and conductive parts; the distance through insulation (solid insulation, film or cover thickness, number of layers) from the standard that applies to the product (for example EN 60730-1 20.3 for controls, IEC 60335-1 29.3 for appliances, IEC 62368-1 5.4 for ICT), written in `architecture.md` with the clause.
   The architect draws the mechanical parts in stage 2 with their real footprints (battery holder, relays, terminals, connectors, fuse, module, display, fixings): `footprint`, `side`, `at`/`rot` where it decides the place, and `pins` with the nets of the isolation groups; the rest of the circuit as `area_mm2` items. `uv run hwflow floorplan <proj> --stage arch` (seconds) must pass before stage 2 ends: overlaps, through-hole pins under parts on the other face, region fit, mains corridors and isolation, area left. The architect gets at most 2 fix runs after the first; a FAIL after them goes to the product person with the numbers, not to stage 3 (in thermo-e2e-5 the holder-over-coil-pins and terminal-corridor failures surfaced only in stage 4 and cost an architecture rework).
   Stage 2 is not done until `uv run hwflow floorplan <proj> --stage arch` passes and `uv run hwflow floorplan <proj>` gives PASS (or PASS with risks) and `uv run hwflow check <proj> --json` has no `mains-fuse` error and no `mechanical` warning left unanswered in `architecture.md`; a failure that needs a size, layer, construction or spec change goes to the product person. Do not set `board.width_mm`/`height_mm` to a size the floorplan was not checked at. Then run the decisions pass.
3. Parts (subagent `hw-parts`). For each major IC, start from a reference design (`uv run hwflow ref search <mpn|function words>`: designs in examples/, projects/, the layout blocks and the open-hardware index, with the sub-circuit, source and licence). For each block, choose a part that is in stock and has a KiCad symbol and footprint. Each IC, connector, relay and fuse gets `limits:` from its datasheet and each rail a `v_max`, so `hwflow check` compares pin limits with net voltages before review (docs/reference-reuse.md). Record alternatives and the reason for the choice in `notes/parts.md`. Fill `mpn`, `lcsc`, `price_usd`, and `datasheet`, and fill the SPICE model parameters from the datasheet. The parts table also gives, for each part, the mechanical drawing it was checked against (pin count, pad span, body, height), the assembly side and method (SMT, THT or hand solder: this goes into the component placement list), and for connectors the entry direction. A footprint with no cited drawing is a placeholder, and placeholders do not reach layout. Each modelled part gets `spice.mpn` (the part its model or fit comes from); the non-BOM cost lines go in `cost.extra`, so `hwflow check` recomputes the unit cost (`cost-limit`, `cost-doc`).
   **Library blocks first.** Each `hw-parts` agent runs `uv run hwflow block match <proj>`: before capture it lists the library blocks that the architecture and parts notes name by part or function. A block that covers a function (a driver IC block against a discrete H-bridge, a boost cell, an MCU module with its decoupling) is the default; `notes/parts.md` gives the reason for every listed block not taken (a number: current, voltage, cost, size).
   **Stage-3 exit gate**, in this order, all before `hw-circuit` starts (they were 2.8 h of rework when review found them after capture):
   1. Merge the parts tables; if the unit cost is over a must limit, ask now (see cost above).
   2. Floorplan with the real footprints (the confirmation of the stage-2 mechanical check): put each chosen footprint of a floorplan item into `design.yaml` (`footprint: Lib:Name` on the item in place of `size_mm`, the real `height_mm`, and for connectors the `envelope_mm` of the chosen mating part), then run `uv run hwflow floorplan <proj>` (about a minute). A placeholder footprint (`size_mm` or a generic package) for a part that has a chosen MPN is a stage-3 blocker. A failure goes back to the part choice (a smaller package, another entry direction) or to stage 2, not on to the circuit. Floorplan rework is capped: at most one agent and two more floorplan runs; if it still fails, ask the product person with the numbers from `build/FLOORPLAN.md` (board size, two faces or stacked boards, which part swaps, each with its cost) instead of another cycle. An illegal quick placement (`placement` failure) lists every overlapping part by name: fix those parts or regions, not the routability.
   3. Parts review: `hw-reviewer` in **parts mode**, alone in its message (a foreground message returns only when every agent in it is done: a review next to a long agent leaves its findings idle). Brief it with the project path, `notes/parts.md` and the datasheet notes: it reviews datasheets, models and the BOM (leakage and other limits at their maximum and at temperature, ESR ranges, DC-bias capacitance, abs-max against the rails, shoot-through and other topology risks of the chosen parts, library blocks not taken, stock and price at the build quantity, the model's source part against the BOM MPN), not the circuit. The moment it returns, start one `hw-parts` fix pass with every finding that needs a part change, and put the others in the `hw-circuit` brief.
   4. The decisions pass, with the product questions of the review in the same round.
4. Circuit and simulation (subagent `hw-circuit`). Write `design.yaml` with the reference circuits from the datasheets. Add a testbench measure for each requirement that SPICE can verify, and tag it with `req`. Capture and simulate block by block: run `uv run hwflow build <proj> --until sim` as soon as the first block and its testbench are captured, then after each further block, until check and ERC have zero errors and every measure passes. Monte Carlo runs once, in the final verdict build of stage 8 (`--mc 100`), not in stage 4 or 5: design to the worst case instead (the tolerance and temperature corners in the testbench). A change to a model that every testbench instantiates (a project `.lib` subcircuit of the full board) makes the next build a cold run of every testbench (10 minutes on thermo-e2e-3): try the change on one `build/sim/<name>.cir` with `ngspice -b` first, then put it in the shared model once, with any other model edit, and run that build with `--detach`. Keep `board` and `floorplan`; name the real parts of each floorplan item (`refs`). Stage 4 is not done until `uv run hwflow floorplan <proj>` (which now also runs the layout proofs: escape, barrier, cut, corridor, padiso) gives PASS or PASS with risks with the captured parts, and every isolation risk it lists is fixed or answered in `notes/circuit.md`. Before the stage ends, the circuit also covers these points:
   - every isolation member net has `layers` (more than 2 layers) and `min_width_mm` (a neck must not melt before its fuse opens);
   - each isolation group has `between_mm`;
   - every bypass capacitor has `decouples:`;
   - every voltage-drop requirement is split into a device share and a copper share (`budgets:`, kind `copper_r`);
   - every wake or interrupt source is on a pin that can wake the MCU, and every strap pin is in its safe reset state.
   Fill the contract numbers that come from circuit results, and run `uv run hwflow fw <proj>` until it reports 0 errors.
5. Review (subagent `hw-reviewer`). The parts-mode findings are already in; this review is of the captured design, and its brief names its scope: the delta since the parts review (the circuit around the parts, the parts changed since) and the layout-relevant items below, not the datasheets and BOM again. It does an independent review of things that the tools do not check: datasheet application notes, absolute maximum ratings, ESD and reverse-polarity protection, pull-ups, enable and boot pins, connector pinouts, and thermal limits. It also reviews the layout-facing points that cost the most when found late: the isolation groups and their distances (between_mm included), the layers of hazardous nets, the connector and mating envelopes against cuts and walls, footprints against their drawings, and the assembly and component placement list. Fix every finding at `must` level. Product questions among the findings go out in one round at once, while the rest is fixed. Brief `hw-circuit` with all the findings of the review in one message: it fixes them as one batch and runs one build and one simulation pass (`--until sim`, no Monte Carlo), not one build per finding. After the fixes, re-run `hwflow floorplan` if a part, net or region changed. Then one delta review of the changed refs. A `must` it leaves, or a later change before layout, goes into the sign-off review; there is no third review in stage 5. The stage-5 review also covers the widths and layers that routing depends on (power and battery nets from their current, crystal and other sensitive nets' layers and keep-outs, footprint rule areas): run 4 found them at sign-off and spent 2 h re-laying out.
6. Optimize. If the requirements name optimization criteria, write the `optimize` section, run `uv run hwflow optimize <proj>`, show the trade-off to the product person if it changes cost or a spec, and apply it with `--apply`. Then rerun stage 4.
6b. Floorplan. Before layout, re-run `uv run hwflow floorplan <proj>` on the reviewed design with the real footprints. It must give PASS (or PASS with risks). A failure that needs a size, layer, construction or spec change goes to the product person; a part that does not fit its region goes back to stage 3 or 4.
7. Layout (subagent `hw-layout`), in parallel with firmware (stage 9). It starts from the floorplan: the placer keeps parts inside their regions, so no anchors are needed for them. It runs `uv run hwflow build <proj> --until layout --auto --brief`, which places, routes, repairs DRC errors and retries on its own, and does not hand-tune coordinates. It escalates only residual errors that need judgment (footprint keep-outs, creepage, board size or layer changes) with an error list and a PNG; you take size, layer and cost decisions to the product person. A pin swap changes `design.yaml` only; `uv run hwflow fw <proj>` must still report 0 errors.
8. Sign-off. A board goes to fabrication only once, so every gate below must hold before `state.md` becomes `done`:
   - `uv run hwflow build <proj> --mc 100` gives a PASS verdict, with Monte Carlo yield of 99% or more, and the measures run at the temperature extremes of the requirements (`temps`). Monte Carlo is cheap (100 runs of 16 analyses took 25 s on thermo-e2e-8): `hwflow evidence <proj> --refresh` runs it with `--until sim` (never a layout), trace turns each yield into a measure of the requirements that analysis carries, and the final verdict build reuses it.
   - Every active part whose vendor publishes a SPICE model uses that model (`spice.lib`, `spice.source: vendor`). Datasheet fits use `spice.source: fit`, and project-written models use `behavioral`. The report lists the parts that still use generic models. For each one, `notes/models.md` says why the generic model is enough for the claim it supports.
   - `hw-reviewer` ran in **sign-off** mode on the final design: a delta review of the refs and nets changed since the stage-5 review plus the as-built layout items (`hwflow nets`, isolation, `layout?` rows of `hwflow trace`), not a full re-review; and a delta review of its fixes has zero `must` findings.
   - `uv run hwflow trace <proj>` shows zero failing and zero unverified `must` requirements (`uv run hwflow evidence <proj>` exits 0). Unverified `should`/`could` requirements do not fail the verdict; list them in `SUMMARY.md`.
   - `uv run hwflow fw <proj>` reports 0 errors, and every `open` item in `interface.yaml` is a product question or done.
   - `SUMMARY.md` has a first-article risk list: what the simulation cannot prove, and the bench test that proves each item on the first board.
   Sign-off edits after a clean layout are incremental. hwflow keeps the placement of the last clean layout (`build/placement.good.json`), and the next build's attempt 1 starts from it: unchanged parts stay where they were, only the parts an edit adds, changes or collides with are re-placed, and routing runs again (docs/layout-flow.md, "Incremental layout"). Sort the review findings before editing:
   - routing-only edits (a net `width_mm` or `layers`, a track keep-out) and part swaps with the same footprint (MPN, value) keep the placement: apply them as one batch and run one build (`--auto`, no `--reuse`, never delete `build/`);
   - edits that move a few parts (a part or block pinned, a new keep-out or region over placed parts, one footprint change) are re-placed locally in the same build; prefer a rule (`budgets:` `copper_len`, a region) to fixed coordinates, which collide with the placed board;
   - edits that invalidate the layout (new parts or footprints on more than a quarter of the movable parts, board size or layers, isolation distances) are a `decision`: in delegated mode decide and log it, else ask the product person whether the gain is worth a new layout. A `should` or `nit` that would invalidate the layout goes to the first-article list in `SUMMARY.md` instead.
   The build's attempt line says `incremental from the last good layout`, and REPORT.md lists the parts kept, changed, in conflict and re-placed. If the incremental build does not converge, take back the edit whose parts it names as in conflict (or turn it into a rule) and build once more; at most two sign-off layout builds, then the edit is a product decision.
   If a gate cannot hold, the state is `blocked`, not `done`, and `SUMMARY.md` says which gate failed.
   When every gate holds, the first lines of `state.md` are `stage: 8-signoff` and `status: done`. Runners look for that exact `status:` line.
   Evidence (mechanical, at most 15 min; docs/design-yaml.md, "Evidence from hwflow results"). Do it after the last design edit: a manual record binds the evidence hash, so any later `design.yaml` or requirement edit makes it stale (`auto:` evidence never goes stale).
   1. `uv run hwflow evidence <proj> --refresh`: runs the firmware host tests when they are not current and Monte Carlo when it did not run on the current design, then prints the plan.
   2. `computed`: hwflow results (tagged measures with their Monte Carlo yield, layout checks, host-test `CHECK`s that name the id) all pass. In one pass, keep the ids whose results prove the acceptance criterion and run `--accept <ids>`; a `test` requirement accepted this way puts its bench test on the first-article list. Do not accept a result that proves something else (a firmware check that the RTC is set does not prove the crystal drift).
   3. `needs a check`: tag the measure or layout check with `req:` (a layout check is the layout agent's), or report the gap.
   4. `needs a record`: `--stubs` writes `notes/evidence/<id>.md`. Fill each from what `notes/` already holds (the datasheet page, the calculation, the inspected drawing); one `general-purpose` helper with `model: sonnet` fills the datasheet stubs in one batch. Delete the stub marker line, then `--set <ids>=pass` (or `fail`). One shared artifact with a section per id is fine (`--set R8,R13=pass:notes/evidence/datasheets.md`).
   5. `uv run hwflow evidence <proj>` exits 0.
   Run a full `uv run hwflow build <proj> --mc 100` and `uv run hwflow trace <proj>`. Write `SUMMARY.md` for the product person: what the board does, the requirement table with status, the cost, the size, the open risks, and the decisions they made. Set `state.md` to `done`.

9. Firmware (subagent `fw-firmware`). It starts when the contract and the pinout are frozen: after stage 5, `uv run hwflow fw <proj>` gives 0 errors and `interface.yaml` has no open signal. Launch it in the same message as the stage-7 `hw-layout` subagent (both in the foreground), not after sign-off. Layout changes the pinout only through a pin swap in `design.yaml`. After a pin swap, re-run `hwflow fw` and send the changed signals to the firmware agent (or re-brief it). It writes the product as modules on the shared event-queue framework (`fw/framework/`), from the skeletons and event list that `hwflow fw --scaffold` generates out of `interface.yaml`, with a simulated board and host tests (`make -C projects/<name>/fw test`). A SW timing that the board cannot meet, or a SW cost that no budget carries, comes back to you as a conflict: route it to stage 4 or to the product person. The stage is done when the host tests pass and the bring-up checklist in `partition.md` lists every firmware item that needs the real board.

## Loop discipline

- In headless mode, do not end your turn between stages. Go from one stage to the next in the same turn. End your turn only when you wait for product answers, when `state.md` is `done`, or when you are blocked and wrote the reason in `state.md`.
- `hwflow build` prints `build/REPORT.md` at the end of its output. Do not read the file again after a build. Do not read `build/status.json` unless you need a detail. Agents read results as JSON: `--json` on `check`, `build`, `trace`, `nets`, `ref`, `block match`, and `uv run hwflow summary <proj> --json` after a detached run (compact, versioned schemas; docs/reference-reuse.md). Brief subagents to use them.
- After the product person approves a change of layers, board size or cost, run `uv run hwflow approve <proj>`; otherwise `check` reports the change as an error. After an answer that changes a requirement, run `uv run hwflow approve <proj> --requirements`. For layout, `uv run hwflow layout <proj> --auto` (or `build --auto`) does placement, routing and DRC in one call, and `build --brief` prints only what changed.
- Fix the root cause. Do not widen a measure limit to make it pass. If a limit is wrong, the requirement is wrong, and the product person decides.
- A derived limit is different. A derived limit is one computed from a product number, for example a sleep current from a battery life. When it misses but the product number still holds, re-allocate the budget in `notes/` with the arithmetic and record it in `requirements.yaml` (source: the re-allocation note, `derived` in the text or source). You do not need to ask. A re-allocation changes numbers only: a new condition in the acceptance (a firmware restriction, a narrower range, another method) is a spec change for the product person, and `hwflow check` reports it (`acceptance`). Margins above the product number are `should`, and a `should` miss never blocks a stage.
- `hwflow floorplan` failures and `hwflow check` errors with code `escape`, `barrier` or `cut` are layout feasibility proofs: no placement or router can meet them with these parts, nets and board. Each message names the stage that fixes it (parts: a package with the pitch named; circuit: narrower nets; architecture: board, layers or fixed geometry). Fix them there before stage 7; never start a layout with one open.
- A `routability-prediction` FAIL of `hwflow floorplan` is the congestion gate: windows of the quick placement where the crossing nets need 6 x or more the tracks that fit (boards that routed stay under 5 x). It names the hot spot, its parts, the wide nets (and the budget that widened them) and the moves; do one of those moves (spread the named movable parts with a region, give a budget's high-current path its own net, parts to the other face) and re-run the floorplan. More layers or a larger board is a product decision. In thermo-e2e-6 this check was only a risk and the layout spent 1.3 h on a board that left 27-41 nets open.
- The layout stage ends with a `layout diagnosis`. When it says `BLOCKED ... go back to <stage>`, the loop goes back to that stage, not to the router: stage 3 (parts) for a package or part choice (it names the pitch needed and the nets), stage 4 (circuit) for net widths or currents, stage 2 (architecture) for board size, layers or part count, which you take to the product person with the numbers. Do not ask the layout agent for another cycle and do not run `--retry-layout` yourself: hwflow blocks a new layout build of the same parts, nets and board until that change is made.
- Spend at most 3 build cycles on the same failing measure. Then re-allocate it (if it is derived), change the circuit in one step you can justify, or ask the product person with the numbers. Do not spend hours on a small miss.
- If a stage does not converge after 6 iterations, write what you tried in `state.md`, and either ask the product person or change the architecture.
- Delegate to subagents with a compact, self-contained brief: the project path, the stage goal, the files to read, the decisions already taken, and the `design.yaml` sections that the stage needs (paste the few lines, for example the `sim:` format or the net class keys). Tell the subagent not to re-read `docs/design-yaml.md` beyond the named section and not to explore `examples/` or other projects unless the brief says so. A subagent returns a short result, not file dumps.
- Rework briefs are narrow: name the one failure to fix (with its numbers, for example the floorplan line), the files and the `design.yaml` sections the agent may change, what is decided and must not move, and the stop rule (for a floorplan rework: two floorplan runs, then return the numbers). Size each brief so it fits the agent's turn limit (`maxTurns` in `.claude/agents/<name>.md`; hw-architect has 60): split a larger rework into two agents, one after the other. Tell every agent with more than a few edits to keep a checkpoint, `notes/progress-<agent>.md` (done, next, any file left half-edited), and to stop editing and return when it has used about four fifths of its turns. When an agent stops at its turn limit, read its checkpoint and `git diff`-style changes, fix or finish the half-done edit yourself if it is small, and brief a new agent with only the items left; record the stop in `state.md`.
- Reviews and parallel agents: a foreground message returns only when every agent in it is done. Do not put a review in the same message as a long agent; run it alone (or next to agents no longer than it) and start the fix agent the moment the review returns.
- One writer per file: while a subagent owns `design.yaml` (circuit, layout), send it the change with SendMessage instead of editing the file yourself.
- Parts can run in parallel: launch one `hw-parts` subagent per block group in the same message (foreground). Each owns its own datasheet notes and returns its table. They do not edit `design.yaml`; you merge the tables into `notes/parts.md`.
- Waste found in the timed runs (thermo-e2e-4 and -5, docs/stage-budget.md), each now a rule:
  - Every Agent call passes `run_in_background: false`. Never poll for an agent's files with `until [ -f ... ]; sleep` loops (4 and 5 min of polling in stage 1 of both runs).
  - Stage 1 does no part survey. A conflict that depends on which part exists (a Wi-Fi module that runs from the cells, for example) gets the assumption and at most 5 searches for feasibility; the survey belongs to the architect in stage 2 (run 5: 22 searches in stage 1, the requirements agent hit its turn limit, three spawns, 21 min against 5 min in run 4).
  - Stage 3: the parts fix pass takes only the `part change` findings of the parts review, at most 8, with a 15-minute time box; the `circuit` findings go into the `hw-circuit` brief and the rest to the first-article list (run 5: 20 findings, a 21-minute fix pass with 10 web lookups).
  - A floorplan rework is one `hw-architect` agent, at most two floorplan runs, 15 minutes; brief it with at most two candidate geometries to test, and tell it to test a candidate with `hwflow floorplan` rather than reason it out (run 5: one rework took 58 min, five floorplan runs and two single model turns of 19 and 17 minutes).
  - Reviews: parts review (stage 3), the stage-5 review (delta from the parts review), and at most one delta review in stage 5 after the fix batch. A later change before layout goes into the sign-off review, which is itself a delta review of what changed since stage 5 plus the as-built layout items, not a full re-review (run 4: six reviews, 55 min on the critical path, two delta reviews in stage 5).
  - Sign-off layout builds are the layout agent's: you do not run layout builds yourself, and the two-build cap of stage 8 counts every build. Batch every sign-off edit before the build; one layout build costs 8 to 25 min (run 4: the lead ran six layout builds after the final layout pass, about 105 min, and one of them was refused as blocked).
  - You do not read datasheets or PDFs yourself; a helper agent (`general-purpose`, `web-fetch`) for a lookup or a summary draft gets `model: sonnet`.
  - Stage-4 builds with `--until sim` take about 10 s: build after each block as the stage says; the cost of stage 4 is model time, so give `hw-circuit` the parts table and the review findings in one brief and do not re-brief it per finding.
- Run subagents in the foreground and wait for their result in the same turn. Do not use background agents, ScheduleWakeup, or loops that wait for a later message. In headless mode, the session ends when your turn ends, and background work is lost.
- A build you started must finish inside your turn. Run it as one blocking call with a timeout (`timeout 1500 uv run hwflow build ...` as a foreground Bash call with a matching Bash timeout, up to 10 minutes per call); if it needs more, start it with `uv run hwflow build <proj> ... --detach` and wait with `uv run hwflow run wait <proj> <run_id>` (one blocking call of at most 580 s each; exit 2 means still running, call it again; 0 or 1 means finished). Never end a turn while a build you started is running, and never write "waiting for the build" as a closing message: the session ends with the turn and kills the build. This also applies to every subagent you brief.
- Delta review: after any late change that adds or moves parts (a circuit fix after stage 5, a protection added for a test), launch `hw-reviewer` in delta mode before layout or sign-off. Brief it with the changed refs only (`git diff`-style list), so it checks them against the stack, clearances, the connector area, the datasheet limits and the testbench `realism:` notes. Do not wait for the full review at sign-off to find an invalidated layout assumption.
- If you find that a requirement or a testbench measure is inconsistent with another one (for example, a full-gain test tone placed above the bandwidth corner), record it in `conflicts.md` with the arithmetic. In headless mode, write it as a question for the product person. Do not change the limit yourself.

## requirements.yaml format

```yaml
product: one line
optimize_for: [{criterion: cost, weight: 2}, {criterion: noise, weight: 1}]
requirements:
  - id: R1
    priority: must
    text: "Runs 7 days on a 1000 mAh Li-ion cell"
    acceptance: "average current <= 5.9 mA at 3.7 V"
    verification: simulation        # simulation | layout | datasheet | analysis | inspection | test
    evidence: {status: not_checked}  # at sign-off: {auto: [sim|layout|fw_test|cost]} or a record written by `hwflow evidence --set`; docs/design-yaml.md
    source: "PM round 1, q2"
```
